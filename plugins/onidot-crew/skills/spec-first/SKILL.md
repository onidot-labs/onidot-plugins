# spec-first

동작을 바꾸기 전에 "무엇이 되면 맞는가"를 먼저 정한다.

## 1. 기준 명세 찾기

1. 연결된 지식 저장소, 저장소 문서, 이슈에서 이 기능의 명세를 찾는다.
2. 기존 시험과 코드 주석에서 현재 의도된 동작을 확인한다.
3. 찾은 명세가 현재 코드와 어긋나면 어느 쪽이 맞는지 확인한다. 추측으로 고르지 않는다.

## 2. 없으면 짧게 만든다

| 항목 | 내용 |
| --- | --- |
| 목표 | 이 변경으로 무엇이 가능해지거나 고쳐지는가 |
| 범위 | 바뀌는 동작과 영향받는 부분 |
| 비목표 | 이번에 일부러 건드리지 않는 것 |
| 수용 기준 | 확인 가능한 문장. "~하면 ~된다" 형태 |

- 수용 기준은 시험으로 옮길 수 있어야 한다. "잘 동작한다"는 기준이 아니다.
- 경계 조건과 실패 경우를 최소 하나씩 넣는다.
- 명세는 연결된 지식 저장소가 있으면 그곳에 둔다.

## 3. 기준에서 끌어내기

- 계획의 단계와 완료 기준은 수용 기준에서 나온다. `onidot-crew:plan` 스킬로 넘긴다.
- 시험은 수용 기준마다 하나 이상 만든다. `onidot-crew:tdd` 스킬로 넘긴다.
- 검증 때 이 수용 기준을 그대로 쓴다. `onidot-crew:verify` 스킬로 넘긴다.

## 4. 무게 조절

| 변경 | 명세 |
| --- | --- |
| 한두 줄 버그 수정 | 수용 기준 한두 문장. 별도 문서 없이 위임 지시나 커밋 설명에 둔다 |
| 기능 하나 | 짧은 변경 명세 |
| 여러 모듈, 되돌리기 어려운 변경 | 변경 명세와 승인 |

작은 수정에 별도 문서나 재승인을 강제하지 않는다. 순수 문서 수정이나 동작을 바꾸지 않는 편집에는 이 스킬을 쓰지 않는다.


## 서브에이전트로 실행 중일 때

역할 에이전트 안에서 이 스킬을 쓸 때는 사용자에게 묻기, 문서 저장, 승인 요청, 다른 역할에 맡기기를 직접 하지 않는다. 그런 단계는 반환에 '메인이 할 일'로 적는다. 이 스킬이 지금 자기 역할에게 맡기라고 하면 직접 수행한다.

## 점검 목록

- [ ] 기존 명세를 먼저 찾았다.
- [ ] 수용 기준이 확인 가능한 문장이다.
- [ ] 비목표를 적었다.
- [ ] 계획과 시험이 수용 기준과 연결된다.
- [ ] 변경 크기에 맞는 무게로 썼다.
