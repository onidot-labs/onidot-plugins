# review-work

검토는 "좋아 보인다"가 아니라 기준과의 대조다.

## 1. 대조 기준

1. **원래 요청**: 사용자가 실제로 원한 것.
2. **보존 조건**: 바꾸면 안 되는 동작, 구조, 인터페이스.
3. **수용 기준**: `onidot-crew:spec-first` 스킬에서 정한 확인 문장.
4. **저장소 규약**: 지침 파일, 기존 코드의 이름·구조·오류 처리 관례.

기준을 먼저 적고 변경을 읽는다. 기준 없이 읽으면 취향 지적만 남는다.

## 2. 찾을 것

- **결함**: 요청과 다르게 동작한다. 잘못된 결과, 데이터 손실.
- **경계 조건**: 빈 값, 최대값, 동시 접근, 실패 응답, 권한 없음.
- **회귀 위험**: 바뀐 코드를 쓰는 다른 곳이 깨질 수 있다.
- **빠진 시험**: 수용 기준이나 경계 조건을 확인하는 시험이 없다.
- **범위 밖 변경**: 요청과 무관한 수정, 남은 임시 코드.

## 3. 심각도

| 단계 | 기준 |
| --- | --- |
| 치명 | 데이터 손실, 보안 구멍, 운영 중단. 병합 불가 |
| 높음 | 요청한 동작이 틀렸거나 회귀가 확실하다. 병합 전 수정 |
| 중간 | 경계 조건 누락, 빠진 시험. 수정 권장 |
| 낮음 | 저장소 규약과의 사소한 차이. 규약에 없는 취향 지적은 하지 않는다 |

## 4. 지적 쓰는 법

- 근거는 `절대경로:줄` 형식으로 붙인다.
- 무엇이 문제인지, 왜 문제인지, 어떻게 확인했는지를 쓴다.
- 고칠 방향을 짧게 제안한다. 대신 고치지 않는다.
- 추측이면 추측이라고 쓴다.

## 5. 결과 형식

1. 판정: 승인 / 수정 요구. 치명·높음이 하나라도 있으면 수정 요구.
2. 지적 목록: 심각도 순으로.
3. 확인하지 못한 부분.

수정 뒤 재검토는 그 지적과 영향 범위만 본다. 새 변경이 없으면 같은 검토를 반복하지 않는다.


## 서브에이전트로 실행 중일 때

역할 에이전트 안에서 이 스킬을 쓸 때는 사용자에게 묻기, 문서 저장, 승인 요청, 다른 역할에 맡기기를 직접 하지 않는다. 그런 단계는 반환에 '메인이 할 일'로 적는다. 이 스킬이 지금 자기 역할에게 맡기라고 하면 직접 수행한다.

## 점검 목록

- [ ] 대조 기준을 먼저 적었다.
- [ ] 경계 조건과 회귀 위험을 봤다.
- [ ] 지적마다 심각도와 `절대경로:줄` 근거가 있다.
- [ ] 판정을 명시했다.
