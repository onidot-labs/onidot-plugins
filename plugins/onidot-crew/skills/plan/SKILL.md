# plan

일을 받으면 먼저 성격을 판정한다. 판정에 따라 계획의 무게를 정한다.

## 1. 성격 판정

| 일의 성격 | 처리 |
| --- | --- |
| 단순하고 분명한 일 | 바로 처리한다. 계획을 만들지 않는다. |
| 기존 규칙이 있는 일 | 관련 기록·결정을 확인한 뒤 처리한다. |
| 모호하거나 낯선 일, 여러 단계인 일 | 조사부터 한다. scoper와 `onidot-crew:explore-domain` 스킬을 쓴다. |
| 되돌리기 어렵거나 비용·권한이 걸린 일 | 영향과 승인 조건을 먼저 정리한다. |

판정이 애매하면 한 단계 무거운 쪽을 고른다. 단, 단순한 일에 계획이나 다중 에이전트를 강제하지 않는다.

## 2. 큰 일의 계획 순서

1. **읽기 전용 탐색.** 위치는 explorer, 코드 흐름과 영향은 mapper에게 맡긴다. 이 단계에서 파일을 바꾸지 않는다.
2. **결정 정리.**
   - 의도가 분명하면 결과를 바꾸는 핵심 결정만 묻는다. 질문마다 근거와 추천안을 붙인다.
   - 의도가 흐리면 합리적인 기본값을 정하고, 무엇을 가정했는지 밝힌다.
3. **빈틈 점검.** scoper에게 빠진 전제, 모순, 범위 밖 요구를 찾게 한다.
4. **계획 작성.** planner가 단계, 의존 관계, 단계별 완료 기준을 쓴다.
5. **계획 검증.** plan-reviewer가 착수 가능 여부와 막는 요인만 판정한다. 수정은 최대 두 번이다. 두 번 고쳐도 막히면 막는 요인을 사용자에게 보고한다.
6. **승인.** 방향·범위·되돌리기 어려운 결정이 들어 있으면 사용자 승인을 받는다. 그 외에는 바로 `onidot-crew:run` 스킬로 넘어간다.

## 3. 좋은 계획의 조건

- 단계 하나가 위임 한 번 크기다.
- 단계마다 확인 가능한 완료 기준이 있다.
- 단계 사이 의존 관계가 드러나 있다. 동시에 해도 되는 단계를 표시한다.
- 동작을 바꾸는 단계는 `onidot-crew:spec-first` 스킬의 수용 기준과 연결된다.
- 되돌리기 어려운 단계는 따로 표시하고 승인 조건을 적는다.

## 4. 계획 보관

| 범위 | 보관 위치 |
| --- | --- |
| 이번 세션 안에서 끝나는 일 | 호스트의 작업 목록 기능 |
| 세션을 넘기는 일 | `onidot-crew:resume` 스킬대로 진행 기록에 남긴다 |
| 큰 계획서 | 연결된 지식 저장소(onidot Studio Wiki)가 있으면 그곳에 둔다 |

계획서와 진행 기록에 같은 내용을 두 번 쓰지 않는다. 진행 기록에는 계획서 링크만 남긴다.

## 점검 목록

- [ ] 일의 성격을 판정했다.
- [ ] 단순한 일에 계획을 강제하지 않았다.
- [ ] 질문은 결과를 바꾸는 결정으로 한정했고, 근거와 추천을 붙였다.
- [ ] 가정한 기본값을 밝혔다.
- [ ] plan-reviewer 판정을 받았다.
- [ ] 승인이 필요한 결정을 사용자에게 확인했다.
