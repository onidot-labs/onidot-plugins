# run

승인된 계획을 묶음 단위로 실행한다. 메인은 맡기고, 확인하고, 병합한다.

## 1. 역할 고르기

| 단계의 무게 | 역할 |
| --- | --- |
| 작고 분명한 구현 | worker-quick |
| 일반 구현 | worker |
| 어렵고 응집된 구현, 판단이 필요한 구현 | worker-deep |
| 화면 | designer |
| 문서 | writer |

맡길 때는 `onidot-crew:delegate` 스킬의 위임 틀을 쓰고, 계획 때 만든 기준 묶음을 근거에 넣는다. 작업 기록 중이면 단계를 맡기는 Agent 호출의 description 끝에 `[stage:<단계 ID>]`를 붙인다(`onidot-crew:work-record` 스킬 3절).

## 2. 동시 실행

- 수정 파일이 서로 겹치지 않는 단계만 동시에 맡긴다.
- 겹치거나 겹칠 수 있으면 순차로 맡긴다.
- 꼭 동시에 해야 하면 worktree로 격리한다. 병합은 메인만 한다.
- 서브에이전트는 백그라운드로 돌 수 있다. 완료 알림이 오기 전에 결과를 추측하거나 보고하지 않는다.

이 작업이 만든 환경은 만든 즉시 진행 기록에 남긴다. 6절에서 무엇을 치울지 기억이 아니라 이 기록으로 판단하기 때문이다.

- worktree를 만들면 경로·브랜치·기준 커밋을 남긴다. 서브에이전트를 worktree 격리로 돌렸고 변경이 있어 worktree가 남았으면, 결과에 나온 경로와 브랜치를 남긴다.
- worktree에서 compose 스택을 띄울 때는 다른 체크아웃과 겹치지 않는 프로젝트 이름을 `-p <이름>`으로 준다. compose 파일의 `name:`이나 `.env`의 `COMPOSE_PROJECT_NAME`을 그대로 쓰면 메인 체크아웃의 개발 환경과 같은 프로젝트에 붙는다. 프로젝트 이름과 worktree 경로를 남긴다. 공용 개발 환경이 필요해서 compose 파일의 이름 그대로 일부러 띄웠다면 임시 환경으로 기록하지 않는다. 그 환경은 6절의 정리 대상이 아니다.
- 서브에이전트에게 compose 스택을 띄울 수 있는 일을 맡기면 위의 이름 규칙을 위임문에 넣고, 띄운 프로젝트 이름을 반환 형식에 넣는다.

## 3. 단계 게이트

단계는 아래 다섯 관문을 모두 통과해야 닫는다.

1. **계획 정합.** 맡긴 범위대로 했는가. 범위 밖 변경이 없는가. 기준 문서·이전 결정과 어긋나지 않는가.
2. **자동 검사.** qa가 바뀐 범위의 시험·린트·빌드를 실행한다.
3. **실행 증거.** 로그의 통과·실패 줄, 출력, 스크린샷 같은 실제 증거가 있다.
4. **검토.** reviewer가 변경을 원래 요청과 대조한다. 한두 줄 수정은 생략할 수 있다.
5. **정리.** 임시 파일, 디버그 출력, 불필요한 변경이 남지 않았다. 이 단계에서 병합한 worktree와 그 안에서 띄운 임시 환경을 6절대로 지웠거나, 지우지 못한 것을 이유와 함께 기록했다.

## 4. 실패 처리

실패하면 아래 순서로 올린다.

1. 빠진 맥락을 보강해 다시 맡긴다.
2. 방향을 조정하는 메시지를 보낸다.
3. 단계 자체를 다시 쓴다.

같은 단계가 두 번 실패하면 advisor에게 자문한다. 성공한 단계는 다시 돌리지 않는다. 다시 쓰거나 버린 단계의 worktree는 병합되지 않으므로 6절의 "버린 worktree"로 처리한다.

## 5. 마무리

- 모든 단계가 닫히면 `onidot-crew:verify` 스킬로 완료 기준 전체를 확인한다.
- 작업 기록 중이면 단계 반복 안에서 단계 게이트를 통과한 단계마다 `onidot-crew:work-record` 스킬 7절대로 증거를 기록하고 gate 독립 검토를 받은 뒤 `complete_work_stage`로 닫는다(여러 단계를 함께 닫을 때는 `stages` 배열 한 번, 7절 23번). 모든 단계가 끝나면 같은 절차로 작업을 완료한다.
- 확인과 작업 완료 기록이 끝나면, 사용자에게 보고하기 전에 6절대로 이 작업이 만든 worktree와 임시 환경을 정리한다. 증거를 기록하기 전에 정리하지 않는다.
- 진행 상황은 `onidot-work`의 작업 기록 도구가 있으면 `onidot-crew:work-record` 스킬대로 단계마다 시작·끝 흐름 이벤트로, 없으면 `onidot-crew:resume` 스킬대로 남긴다. 멈출 때도 남긴다.
- 사용자 보고는 결과를 먼저 쓰고, 완료·미완료·미검증을 나눈다.

## 6. worktree와 임시 환경 정리

작업이 끝나도 worktree를 남겨 두면 디스크가 계속 불어난다. worktree마다 의존성 설치본이 따로 쌓이고, 그 안에서 띄운 compose 프로젝트의 볼륨·컨테이너·이미지가 남고, 상위 디렉터리를 색인하는 도구가 그것까지 색인한다. 이 작업이 만든 것은 이 작업이 치운다.

**대상.** 2절대로 진행 기록에 남긴 것만 치운다.

- 메인이 만든 worktree, 서브에이전트의 worktree 격리로 남은 worktree
- 그 worktree에서 이 작업이 띄운 compose 프로젝트의 컨테이너, 볼륨, 그 프로젝트가 빌드한 이미지

사용자가 만든 것, 다른 세션이 쓰는 것, 기록에 없어 이 작업이 만들었는지 확인할 수 없는 것은 건드리지 않는다.

**시점.**

- 단계 worktree는 그 단계를 병합한 직후에 지운다.
- 작업 전체의 worktree는 5절 순서대로 증거 기록과 작업 완료 뒤, 보고하기 전에 지운다.
- 이때 아직 푸시·병합 전이라 조건 2를 못 채워 남긴 worktree는, 사용자 요청으로 푸시나 PR을 처리한 직후 이 절을 다시 적용한다.
- 멈추거나 인계할 때는 아직 병합·확인하지 않은 worktree를 지우지 않는다. 병합을 마친 것은 지운다. 남긴 것은 진행 기록에 적는다(`onidot-crew:resume` 스킬 2절).
- 일을 이어받으면 기록에 남은 worktree·compose 프로젝트를 이 절의 조건으로 다시 확인하고, 그사이 병합됐으면 지운다(`onidot-crew:resume` 스킬 1절).

**지워도 되는 조건.** 아래를 모두 만족해야 한다. 확인 명령이 오류로 끝나면(upstream 없음, 분리된 HEAD 등) 그 조건은 만족하지 않은 것으로 본다.

1. `git -C <worktree> status --porcelain --untracked-files=all` 출력이 비어 있다.
2. HEAD의 커밋이 다른 곳에도 있다. 둘 중 하나여야 한다.
   - `git -C <worktree> merge-base --is-ancestor HEAD <병합 대상>`이 종료 코드 0으로 끝난다.
   - `git -C <worktree> log @{u}..HEAD`가 종료 코드 0으로 끝나고 출력이 비어 있다.
3. 그 worktree를 작업 디렉터리로 쓰는 프로세스가 없다. `lsof -a -d cwd -Fn | grep -F <worktree 경로>`로 확인한다.
   - 다른 세션이 쓰는 중이면 지우지 않는다.
   - 메인 자신의 작업 디렉터리면 먼저 메인 체크아웃으로 옮긴다. 하네스가 만든 세션 worktree라면 하네스의 worktree 도구로 정리한다.
4. worktree 안에 증거로 링크한 파일(시험 로그, 스크린샷, 보고서)이 없다. 무시 대상 파일은 status에 나오지 않지만 `git worktree remove`가 함께 지운다. 증거가 있으면 먼저 worktree 밖으로 옮기고 링크를 고친다.
5. 그 worktree를 기준 경로로 둔 컨테이너가 남아 있지 않다. 아래 순서 1에서 내린 프로젝트를 뺀 뒤 `docker ps -a --format '{{.Names}} {{.Label "com.docker.compose.project.working_dir"}}' | grep -F <worktree 경로>`에 나오는 컨테이너가 없어야 한다. 하나라도 나오면 지우지 않고 "사용 중(컨테이너)"으로 보고한다. 공용 개발 환경을 worktree에서 띄웠다면 worktree를 지울 때 그 compose 파일과 bind mount 데이터가 함께 사라지기 때문이다.

**compose 프로젝트를 내릴 조건.** worktree를 지우기 전에 확인한다.

- 프로젝트 이름이 2절대로 기록에 있다.
- 그 프로젝트의 컨테이너가 이 worktree에서 떴다. 컨테이너 라벨 `com.docker.compose.project.working_dir`가 이 worktree 경로 안이어야 한다(`docker ps -a --filter label=com.docker.compose.project=<이름> --format '{{.Label "com.docker.compose.project.working_dir"}}'`).
- 다른 경로에서 뜬 컨테이너가 하나라도 있으면 내리지 않고 보고한다.

**지우는 순서.**

1. 내릴 조건을 만족한 compose 프로젝트를 한 번에 내린다. 볼륨을 지울지는 내리기 전에 정한다.
   - 이 작업이 시험·리허설·측정용으로 만든 일회성 프로젝트이고 위의 경로 확인을 통과했으면 `docker compose -p <이름> down --rmi local -v`로 컨테이너, 그 프로젝트가 빌드한 이미지, 볼륨을 함께 지운다.
   - 일회성인지 확실하지 않으면 `docker compose -p <이름> down --rmi local`로 내리고, 볼륨은 남긴 채 지울지 사용자에게 묻는다.
2. 조건 1~5를 확인한다. 하나라도 만족하지 않으면 worktree를 남기고 이유를 기록한다.
3. `git worktree remove <경로>`로 지운다. `--force`는 쓰지 않는다. 거부되면 지우지 말고 이유와 함께 남긴다.
4. `git worktree prune`으로 남은 등록 정보를 정리한다.
5. 병합 대상에 들어간 임시 브랜치는 `git branch -d`로 지워도 된다. 푸시했거나 PR이 걸린 브랜치는 그대로 둔다.

**버린 worktree.** 4절에서 다시 쓰거나 버린 단계의 worktree는 조건 2를 영영 채우지 못한다. 보고에 "폐기 확인 필요"로 모아 사용자 확인을 받는다. 확인을 받으면 위 순서 1로 compose 프로젝트를 먼저 내리고, 조건 3·4·5를 확인한 뒤 `git worktree remove --force`와 `git branch -D`로 지운다. 확인받은 것은 조건 1·2를 건너뛰는 것뿐이다.

호스트 전체를 정리하는 명령(`docker system prune`, `docker volume prune`, `docker image prune`, 다른 프로젝트의 캐시 비우기 등)은 이 작업이 만든 것을 넘어서므로 쓰지 않는다.

**보고.** 지운 것과 남긴 것을 나눠 보고한다. 남긴 것은 경로·브랜치·compose 프로젝트와 남긴 이유(변경 있음, 미푸시·미병합, 사용 중, 경로 불일치, 데이터 볼륨, 폐기 확인 필요)를 적는다.

## 점검 목록

- [ ] 단계마다 무게에 맞는 역할을 골랐다.
- [ ] 동시에 맡긴 단계의 수정 파일이 겹치지 않는다.
- [ ] 만든 worktree와 compose 프로젝트를 만든 즉시 기록했다.
- [ ] 완료 알림 전에 결과를 보고하지 않았다.
- [ ] 단계마다 다섯 관문을 통과했다.
- [ ] 두 번 실패한 단계는 advisor에게 자문했다.
- [ ] `onidot-crew:verify` 스킬로 마무리했다.
- [ ] 이 작업이 만든 worktree·compose 프로젝트를 6절대로 정리했고, 남긴 것은 이유와 함께 보고했다.
