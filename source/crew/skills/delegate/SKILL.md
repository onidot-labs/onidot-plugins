# delegate

맡기는 것은 일이고, 판단은 맡기지 않는다.

## 1. 위임 틀

모든 위임 지시에 아래 여섯 항목을 쓴다.

1. **목적**: 이 일로 무엇을 결정하거나 만들려는가.
2. **원래 요청과 보존 조건**: 사용자 요청의 핵심 문장, 바꾸면 안 되는 것.
3. **근거**: 관련 절대경로, 링크, 판본, 이미 확인한 사실.
4. **허용 변경 범위**: 수정해도 되는 파일, 실행해도 되는 명령. 그 밖은 금지.
5. **종료 조건**: 무엇이 되면 끝인가. 막히면 어디서 멈추고 보고하는가.
6. **반환 형식**: 결론 먼저, 절대경로, 증거, 미확인 사항.

## 2. 크기와 맥락

- 위임 한 번은 계획 단계 하나 크기로 한다. 크면 쪼갠다.
- 전체 대화를 넘기지 않는다. 필요한 최소 맥락만 요약해 넘긴다.
- 첫 지시를 정확히 쓴다. 띄워 놓고 다시 지시하는 왕복을 만들지 않는다.

## 3. 역할 고르기

| 필요한 일 | 역할 |
| --- | --- |
| 계획 전 요청 분석, 빠진 전제 찾기 | scoper |
| 단계·의존·완료 기준이 있는 계획 | planner |
| 계획의 착수 가능성과 막는 요인 판정 | plan-reviewer |
| 고난도 자문, 수정이 두 번 실패했을 때 | advisor |
| 파일·심볼·설정 위치 찾기 | explorer |
| 코드 흐름과 영향 범위 | mapper |
| 기술 문서 조사(출처 링크 포함) | librarian |
| 개발 밖 조사 | researcher |
| 작고 분명한 구현 | worker-quick |
| 일반 구현 | worker |
| 어렵거나 판단이 필요한 구현 | worker-deep |
| 화면 | designer |
| 문서 | writer |
| 오류의 근본 원인 | debugger |
| 변경 검토 | reviewer |
| 시험·빌드 실행과 증거 | qa |
| 완료 주장의 최종 감사 | gate |

비용을 고려한다. 위치 찾기는 저렴한 explorer에게, 판단이 필요한 구현은 worker-deep에게 맡긴다. 무거운 역할을 단순한 일에 쓰지 않는다.

## 4. 동시 위임

- 서로 의존하지 않는 위임은 한 번에 동시에 띄운다.
- 구현 위임은 수정 파일이 겹치지 않을 때만 동시에 띄운다.

## 5. 결과 받기

- 결과를 원래 목표와 보존 조건에 대조한 뒤 쓴다.
- 범위 밖 변경이 있으면 되돌리거나 이유를 확인한다.
- '완료' 보고는 증거로 확인한다. verify 스킬을 따른다.

## 점검 목록

- [ ] 위임 틀 여섯 항목을 모두 썼다.
- [ ] 위임 한 번이 단계 하나 크기다.
- [ ] 비용에 맞는 역할을 골랐다.
- [ ] 결과를 원래 목표와 대조했다.
