# debugging

고치기 전에 원인을 안다. 원인을 모르는 수정은 증상을 옮길 뿐이다.

## 1. 순서

1. **재현.** 실패를 다시 일으키는 가장 짧은 방법을 찾는다. 명령과 입력을 적는다.
2. **증거.** 로그, 스택, 오류 메시지, 입력값, 최근 변경을 모은다. 원문을 읽는다.
3. **가설 순위.** 가능한 원인을 나열하고 증거와 가까운 순으로 줄 세운다.
4. **하나씩 검증.** 가장 유력한 가설부터 확인한다. 확인 방법은 로그 추가, 값 출력, 최소 사례 등이다.
5. **근본 원인.** "왜"를 더 물어도 답이 같아질 때까지 내려간다.
6. **수정과 회귀 시험.** 원인을 고치고, 그 원인을 잡는 시험을 추가한다. `onidot-crew:tdd` 스킬을 따른다.
7. **확인.** 처음 재현 방법으로 다시 실행해 사라졌는지 본다. 관련 시험도 돌린다.

## 2. 하지 않는 것

- 여러 곳을 한꺼번에 바꾸지 않는다. 무엇이 고쳤는지 알 수 없게 된다.
- 재현 없이 고쳤다고 하지 않는다.
- 시험을 끄거나 기대값을 바꿔 통과시키지 않는다.
- 예외를 삼켜 증상을 숨기지 않는다.

## 3. 증상과 원인 구분

| 증상 | 근본 원인의 예 |
| --- | --- |
| 널 참조 오류 | 초기화 순서, 빠진 검증 |
| 가끔 실패하는 시험 | 시간 의존, 공유 상태, 순서 의존 |
| 운영에서만 실패 | 개발에서 우회한 경로, 설정 차이 |

## 4. 막혔을 때

- 수정이 두 번 실패하면 멈추고 advisor에게 자문한다. 재현 방법, 증거, 기각한 가설을 함께 넘긴다.
- 원인 규명 자체를 맡기려면 debugger에게 위임한다.
- 기각한 가설과 그 근거를 기록한다. 같은 길을 다시 가지 않게 한다.

## 5. 보고

- 재현 방법, 근본 원인, 수정 내용, 회귀 시험 이름, 확인 결과.
- 확인하지 못한 부분은 미검증으로 적는다.

## 점검 목록

- [ ] 재현 방법을 적었다.
- [ ] 증거 원문을 읽었다.
- [ ] 한 번에 하나만 바꿨다.
- [ ] 회귀 시험을 추가했다.
- [ ] 처음 재현 방법으로 다시 확인했다.
