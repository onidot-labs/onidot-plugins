# tdd

시험이 먼저다. 시험이 실패하는 것을 본 뒤에 구현한다.

## 1. 순환

1. **RED**: 수용 기준 하나를 시험으로 쓴다. 실행해서 실패를 확인한다.
2. **GREEN**: 그 시험을 통과시키는 최소한의 코드를 쓴다.
3. **REFACTOR**: 시험이 통과하는 상태를 유지하며 이름, 중복, 구조를 정리한다.

한 번에 수용 기준 하나씩 돈다.

## 2. 올바른 이유로 실패하는가

RED에서 실패 메시지를 읽는다.

| 실패 원인 | 판단 |
| --- | --- |
| 기대한 동작이 아직 없어서 | 올바른 실패. GREEN으로 간다 |
| 컴파일 오류, 오타, 잘못된 import | 시험이 틀렸다. 고친 뒤 다시 RED |
| 환경 문제(DB 없음, 포트 충돌) | 시험 이전 문제. 환경부터 고친다 |
| 처음부터 통과함 | 시험이 아무것도 확인하지 않는다. 다시 쓴다 |

## 3. 시험 범위 고르기

위험에 비례해 고르는 것은 범위이지 생략 여부가 아니다.

- 순수 로직: 단위 시험.
- 저장소·외부 연동: 통합 시험.
- 사용자 흐름: 화면 또는 종단 시험.

## 4. 기존 코드

- 리팩터링은 보호 시험부터 쓴다. 지금 동작을 그대로 고정하는 특성 시험이다.
- 기존 시험이 이미 보호하면 그 범위를 확인하고 부족한 곳만 보강한다.
- 이미 있는 정상 코드와 사용자 변경을 TDD 순서를 지키려고 지우지 않는다. 회귀 시험을 보강한다.

## 5. 보고

- 시험을 먼저 쓴 경우(RED→GREEN)와 구현 뒤 보강한 경우를 구분해 적는다.
- 생략했거나 실행하지 못한 시험은 그 이유와 함께 적는다.
- 통과 여부는 로그의 통과·실패 줄로 적는다.


## 서브에이전트로 실행 중일 때

역할 에이전트 안에서 이 스킬을 쓸 때는 사용자에게 묻기, 문서 저장, 승인 요청, 다른 역할에 맡기기를 직접 하지 않는다. 그런 단계는 반환에 '메인이 할 일'로 적는다. 이 스킬이 지금 자기 역할에게 맡기라고 하면 직접 수행한다.

## 점검 목록

- [ ] 시험이 실패하는 것을 먼저 봤다.
- [ ] 실패 원인이 기대한 동작의 부재다.
- [ ] 구현이 시험을 통과시키는 최소 범위다.
- [ ] 리팩터링 전에 보호 시험이 있다.
- [ ] 보고에 RED→GREEN과 사후 보강을 구분했다.
